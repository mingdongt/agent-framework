# Arize-ai/phoenix — Domain Map
Last refreshed: 2026-05-18 (initial draft by claude-sonnet, needs operator review)

> **Positioning note**: Phoenix is NOT an agent-building SDK. It is an observability and evaluation layer *for* agent systems — you instrument your existing LangChain / LlamaIndex / CrewAI / Claude agents with OpenInference, and Phoenix captures, stores, queries, and evaluates the resulting telemetry. Nothing in Phoenix orchestrates agents or defines agent behavior.

## Architecture in 5 sentences

- The platform is built on OpenTelemetry as its transport layer: application code emits OTEL spans decorated with **OpenInference semantic conventions** (a separate sibling repo at `Arize-ai/openinference`), those spans are collected by a Phoenix server process, and stored in a relational DB whose entire query surface is exposed as a **GraphQL API** (with auto-generated client stubs visible in `src/phoenix/__generated__`).
- There are five load-bearing vertical features that each have their own data model: **Traces** (span trees from running LLM apps), **Evals** (LLM-as-judge scores attached to spans or datasets), **Datasets** (versioned collections of examples), **Experiments** (reproducible runs over a dataset comparing prompts/models/retrievers), and **Prompts** (versioned, tagged prompt templates with a built-in playground for live iteration).
- The deployment surface is intentionally wide: Phoenix runs as a local Python process (`px.launch_app()`), as a Docker container, as a Kubernetes Helm chart, or as a managed cloud service (`app.phoenix.arize.com`) — and the client packages (`phoenix-otel`, `phoenix-client`, `phoenix-evals`, `phoenix-mcp`) are deliberately thin so instrumented applications only install what they need without pulling in the server.
- **OpenInference** is the instrumentation backbone: it is a standalone open standard (Python, TypeScript, Java, Go) with 30+ auto-instrumentation packages for every major LLM provider and framework — it is transport-agnostic (any OTEL collector accepts it) but Phoenix is its primary purpose-built destination.
- The frontend is a TypeScript/React SPA (~36% of the codebase) that serves as the primary UX for span exploration, eval review, dataset management, the prompt playground, and an emerging built-in **AI assistant ("Phoenix Talk")** — the backend/frontend split is clean and the GraphQL layer is the contract boundary.

## Key design choices (taste, not docs)

- **OpenTelemetry as the only ingestion path**: Phoenix does not have a proprietary SDK trace format. All data arrives as OTEL spans with OpenInference attributes. This means any OTEL-compatible collector can forward data to Phoenix, and Phoenix traces can equally be forwarded to Datadog / Honeycomb — a deliberate standards bet that differentiates it from LangSmith's proprietary `RunTree` format.
- **LLM-as-judge evals are server-side, not CLI-only**: The `arize-phoenix-evals` package runs eval templates against spans or dataset rows using any LLM provider (OpenAI, Anthropic, etc.), but evals are first-class objects stored in the DB, queryable via GraphQL, and visible in the UI alongside the spans they annotate — not just a local script that prints scores.
- **Span Notes as a lightweight annotation primitive**: Beyond automated evals, Phoenix ships "Span Notes" — a human-readable annotation attached to any span, supporting collaborative debugging workflows. The fact that `fix: refresh span notes after create` (#13261) was merged very recently indicates this feature is still maturing but is actively prioritised.
- **Experiments close the prompt engineering loop**: A dataset row flows through a prompt template in Experiments, generating a new span and an eval score in one atomic operation. This "dataset → run → eval → compare" loop is the core value proposition for prompt engineers, and it directly integrates with the Playground for interactive iteration.
- **GraphQL over REST for all structured queries**: The primary internal API is GraphQL (REST exists but is secondary). The `__generated__` directory in the Python backend and the TypeScript SPA co-evolve against a shared schema — this gives the frontend type-safe queries and enables the `phoenix-client` package to expose typed methods without hand-written client code.
- **`phoenix-mcp` as a coding-agent integration surface**: Phoenix exposes an MCP server so that AI coding assistants (Claude Code, Cursor, etc.) can query traces and evals directly. This is an early but structurally important bet: observability data becomes a context source for the agents it is observing.
- **Elastic License 2.0, not Apache/MIT**: ELv2 allows free use and modification but prohibits providing Phoenix as a managed service to third parties. This is a deliberate anti-commoditisation choice — competitors cannot wrap Phoenix as a hosted product without a commercial agreement.

## Current pain points

- **OTel GenAI semconv → OpenInference conversion is incomplete**: PR #13267 (`feat(trace): convert OTel GenAI semconv attrs to OpenInference`) was merged 2026-05-15, meaning there is an active mapping layer being built between the emerging OTEL GenAI semantic conventions and Phoenix's OpenInference conventions — a sign that the two standards are currently in tension and the translation is not fully automated.
- **Sandbox span noise from adapters**: PR #13258 (`fix(sandbox): remove adapter-introduced noise from sandbox spans`) landed the same day — the Playground's sandbox execution introduces extraneous spans that pollute the trace view, and the fix required a targeted filter. Suggests the Playground's internal tracing is not cleanly scoped.
- **Client-side tracing for external tools is unresolved** (issue #13173, open, labels: `c/agents c/dx c/traces enhancement triage`): Agent traces that invoke external tools via client-side code are not captured with full fidelity. This is a known architectural gap — the team is actively investigating but has no committed solution.
- **Sessions UX is incomplete** (issue #12731, roadmap milestone "Arize Observe 2026"): Session-level grouping of traces (multi-turn conversations as a unit) is on the roadmap but the UX is not yet shipped. Users working with multi-turn agents currently see individual spans rather than a coherent session view.
- **Monotonic ID generation fix needed**: PR #13245 (`fix: keep generative model fetch id monotonic`) was a correctness bug — fetch IDs were not guaranteed monotonic, which can cause ordering issues in trace reconstruction. Small fix but indicates the data pipeline is still hardening.
- **Docker/Podman on Apple Silicon (SIGILL)**: Issue #12941 is a SIGILL crash on Apple Silicon when running via Podman — a dependency-level binary compatibility problem that blocks local development for a significant share of the target audience.

## Unique advantages

- **Only observability platform with OpenInference as a neutral standard**: Because OpenInference is a separate open spec (not just "Phoenix's internal format"), the ecosystem of instrumentation packages is not locked to Phoenix — but Phoenix is the canonical destination. This creates a flywheel: instrumentors write once, and Phoenix benefits from every new OpenInference adopter.
- **Evals are structurally integrated, not bolted on**: Unlike LangSmith (where evals are a separate product tier) or typical logging solutions (where scoring is done offline), Phoenix evals are stored alongside spans in the same DB, queryable via the same GraphQL API, and rendered inline in the trace UI. The feedback loop from "trace → eval → fix prompt → re-run experiment" is a single workflow.
- **50+ framework integrations through OpenInference auto-instrumentors**: Python, TypeScript, Java, and Go instrumentation packages covering every major LLM provider and framework — the breadth is unmatched by any single-vendor solution.
- **Deployment flexibility without vendor lock-in**: Run fully local (zero external dependencies), self-hosted Docker/K8s, or managed cloud. The same `phoenix-client` package talks to all three. No telemetry data leaves the user's infrastructure unless they choose the cloud option.
- **Playground + Datasets + Experiments as a coherent prompt engineering environment**: The three-way integration of the Playground (interactive iteration), Datasets (versioned test sets), and Experiments (reproducible evaluations over datasets) makes Phoenix more than a passive observer — it is an active development tool for improving LLM application quality.

## Deltas vs LangChain / ADK / pydantic-ai

- **Phoenix is orthogonal to these frameworks, not competitive**: LangChain, ADK, and pydantic-ai are agent-building SDKs; Phoenix is what you plug in *next to* them to observe what they do. Phoenix has OpenInference auto-instrumentors for all three — you can use Phoenix with any of them simultaneously.
- **vs. LangSmith** (the actual direct competitor): LangSmith is LangChain's proprietary SaaS observability product (no self-hosted option outside LangSmith Enterprise). Phoenix is open-source, self-hostable, and provider-neutral. LangSmith's evals are tighter with LangChain's `Runnable` abstraction; Phoenix's evals are framework-agnostic. Phoenix's OpenInference spec is open; LangSmith's `RunTree` format is proprietary.
- **vs. ADK's built-in evaluation**: ADK ships rubric-based LLM-as-judge scoring internally (see `google__adk-python.md`). Phoenix evals are more mature, multi-provider, and integrated into a full trace-browsing UI — but they require deploying a separate service, whereas ADK's eval runs in-process. The two are complementary (ADK for CI-time eval, Phoenix for runtime observability + interactive debugging).
- **vs. pydantic-ai's logfire integration**: pydantic-ai's observability story is Logfire (Pydantic's own OTEL-based platform). Both Logfire and Phoenix accept OTEL spans; Phoenix differentiates with the Experiments/Datasets loop and LLM-specific evals. Logfire is general-purpose APM with LLM awareness; Phoenix is LLM-native with APM primitives.
